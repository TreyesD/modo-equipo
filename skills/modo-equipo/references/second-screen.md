# Second screen for tests (Windows)

Goal: run the test suites on a second display so the user keeps working on the main screen. The skill only needs Windows 10/11 and a display that Windows reports as a non-primary screen. A real monitor works; so does a virtual one.

**Safety contract.** The skill never downloads, installs or runs third-party files by itself. Every step below that downloads, installs a driver or starts a downloaded program is done by the user. If the agent downloads anything for the user, it first names the file, source and size and waits for an explicit yes.

## Option A - a physical monitor

Connect it, press `Win+P`, choose **Extend** (Ampliar). Done.

## Option B - virtual monitor with ParsecVDisplay (verified on Windows 10 Pro)

This is a small tray app that adds and removes virtual displays. It needs the Parsec virtual display driver.

1. Get the release: https://github.com/nomi-san/parsec-vdd/releases (asset `ParsecVDisplay-vX.Y-portable.zip`, under 1 MB). Extract it into its own empty folder.
2. Check the driver. In PowerShell: `Get-PnpDevice -Class Display | Where-Object FriendlyName -match Parsec`. If a "Parsec Virtual Display Adapter" with status OK is listed, skip to step 4.
3. If the driver is missing: the zip contains `parsec-vdd-<version>.exe`, the driver installer signed by Parsec Cloud, Inc. Verify with `Get-AuthenticodeSignature .\parsec-vdd-*.exe` (status must be Valid), then run it as administrator.
4. Start `ParsecVDisplay.exe`. It is **not code-signed** (normal for this open-source project): SmartScreen shows a warning; use "More info" then "Run anyway" only if you accept that. In the tray icon choose **Add display**.
5. If Windows does not extend automatically: `Win+P`, **Extend**.
6. Verify: run `scripts/second-screen/detect.ps1`; it must print `"secondScreen":true`.

Notes:
- Only the driver (steps 2-3) is required by the skill: the screen keeper (`parsec-vdd.ps1`) talks to it directly and needs no `ParsecVDisplay.exe` window. The app is optional, only for adding displays by hand; the skill never starts it.
- A virtual display lives only while something keeps pinging the driver (the screen keeper or `ParsecVDisplay.exe`). When that stops, the display disappears; the skill then falls back to the normal test flow.
- The app can start with Windows (setting inside the app).

## Option C - Virtual Display Driver (alternative, driver-level)

Project: https://github.com/VirtualDrivers/Virtual-Display-Driver (assets named `VirtualDisplayDriver-*.Driver.Only.zip`). Its package is signed (SignPath Foundation). Installing it needs administrator rights and creating the virtual monitor follows that project's own README. This path was **not** completed in testing; prefer Option B.

## What the skill does with it

- `scripts/second-screen/parsec-vdd.ps1 -Ensure [-ScreenId <id>] [-HolderPid <pid>] | -Release [-ScreenId <id>] | -Status`: the screen keeper. Every session id (`-ScreenId`, else `MODO_EQUIPO_SCREEN_ID`, else the Claude Code session, `cc-` + the first 8 characters of `CLAUDE_CODE_SESSION_ID`, else `default`) gets its own virtual monitor: `-Ensure` starts (or reuses) one hidden background process that adds a display through the driver for a new id and hands the same one back to a known id, keeps it while any of that id's holder processes runs and for `-IdleMinutes` (10) after the last one, then keeps it as a spare for the next new session instead of removing it (adding or removing a monitor makes Windows rebuild the display topology and can flash every screen; a spare is removed only after `-SpareMinutes` (720) unused, on `-Release`, or when the keeper stops); the keeper exits when no session and no spare is left. Up to 8 displays (`VDD_MAX_DISPLAYS`). `default` first takes a second screen that already exists (never removed). It prints one JSON line with `screen` (device name) and bounds (exit 0 = the session has a screen). So each Claude session already tests on its own screen; set `MODO_EQUIPO_SCREEN_ID` only to share one between sessions or to name it. While any virtual screen exists it keeps the real cursor on the real screens (`ClipCursor`), lifting the clip while a mouse button is held (window drags) and while the viewer owns the `Local\ModoEquipo.CursorFree` mutex (direct mode); it never overrides a clip another program set, the `screen-keeper-v2/lock-off` flag file turns it off, and a hidden watchdog releases the clip if the keeper dies. `-Release -ScreenId <id>` frees one session's screen, `-Release` alone stops the keeper. A keeper killed while another program keeps its displays alive (the ParsecVDisplay app pings all of them) leaves `screen-keeper-v2/owned.json`; the next keeper gives each id its display back and removes unclaimed ones after 15 s. Close and reopen are self-repairing: `-Ensure` stops a keeper that has not written `keeper.json` for 90 s (hung), drops request files whose holders are gone and that are older than the idle time (a closed viewer), removes a stale `keeper.json`, and when the driver is offline (its driver host crashed, Windows event 10111, usually after many quick add/remove cycles) stops keepers that still hold it open (an open handle keeps Windows from restarting it) and names the exact `pnputil /restart-device` command; driver calls never wait without a bound. Driver protocol from nomi-san/parsec-vdd `parsec-vdd.h` (BSD-2-Clause, credited in NOTICE).
- `scripts/second-screen/detect.ps1 [-Ensure [-ScreenId <id>]]`: by default it only looks and never adds a monitor (adding or removing one makes Windows rebuild the display topology and can flash every screen); with `-Ensure` it first asks the keeper for this session's screen. Prints JSON with `secondScreen` and `screen`.
- `scripts/second-screen/launch-on-second-screen.ps1 -Root <project> [-ScreenId <id>]`: opens the test runner window on this session's screen (from the keeper) and registers the runner as a holder. Exit code 2 and `NO_SECOND_SCREEN` when there is none.
- `scripts/second-screen/launch_offscreen.py -- <exe> [args...]`: starts any windowed program so none of its windows is ever shown on the main screen (with `--screen auto` it asks the keeper for this session's screen, `--screen-id` or `MODO_EQUIPO_SCREEN_ID`, places the program there and registers it as a holder; `--no-ensure` skips that; minimized + suspended start, WinEvent hook, placement before the first visible frame, transparent-move guard). Prints one JSON line; exit 0 placed, 1 launch failed, 2 usage, 3 not Windows, 4 no second screen (started normally), 5 a window stayed on the main screen. Apps that restore their own saved geometry may need an app-specific pre-set (for example Dolphin's `Qt.ini` window geometry).
- `scripts/second-screen/run-tests.ps1`: detects suites (package.json `test` script, pytest `tests/`, `go.mod`, `Cargo.toml`), runs them in order, writes `~/.claude/modo-equipo/tests-last.json` (`status` running|done, result per suite) and `tests-last.log`. Override detection with `<project>/.modo-equipo-tests.json`: `[{"name":"api","dir":"services/api","cmd":"npm test"}]`.
- `scripts/second-screen/screen-viewer.ps1`: borderless window on the main screen that mirrors the second one live on the GPU: Desktop Duplication into a Direct3D 11 texture, shrunk with a Lanczos3 filter (`screen-gpu.ps1`, no pixel returns to the CPU), up to 60 fps, the real pointer drawn on top. The old Magnification API scales with nearest-neighbour, which breaks small text; it is only the fallback when the GPU mirror cannot start. Moving over the image drives the real cursor there (moved by its own 1 ms thread, so no motion is lost and it feels like the normal mouse); a toolbar pill docked at the top centre (per-pixel-alpha window, rests as a thin handle and opens when the pointer reaches it, slides along the top edge from its grip) offers (it only wakes while the pointer is inside the viewer window and is click-through everywhere outside its pill, so it never touches the top edge of the screen, Chrome tabs included) always-on-top (small window only), pointer, next screen (when there are several; `-Screen <device>` / `-ScreenId <id>` pick the one shown), mute (a toggle: while on it mutes, every second, the apps whose windows are on the second screen, including ones that start playing later, and unmutes them when turned off or on close), mouse lock, full screen, keep open, minimize and close. The mouse lock belongs to the screen keeper; the viewer owns the `CursorFree` mutex in direct mode and its lock button writes the keeper's flag file.
- `scripts/second-screen/open-viewer.ps1 [-ScreenId <id>] [-NewScreen]`: one-click entry point. Runs `parsec-vdd.ps1 -Ensure -HolderPid <viewer>` for that session (from the desktop shortcut, with no id at all, every launch creates a NEW virtual screen, session `viewer-<pid>`, so team sessions' tests, which run on their own screens, never land on the one you are using; `-NewScreen` forces that) and shows that screen (no app window), so the screen stays while the viewer is open (a `viewer-<pid>` session becomes a spare as soon as the viewer closes, so reopening reuses that display and adds no monitor; a named session keeps it for the keeper's idle time), then opens the viewer. It never starts `ParsecVDisplay.exe`: if the keeper cannot provide a screen it shows the real reason, and for an offline (crashed) driver it offers to restart only that device (`parsec-vdd.ps1 -RestartDriver`, Windows may ask for admin rights).
- `parsec-vdd.ps1` can also be dot-sourced for `[ModoEquipo.ParsecVdd]` (direct add/remove/keep-alive); `-SelfTest` checks the constants and the keeper rules and never adds a display. `install-desktop-shortcut.ps1` creates a desktop shortcut for it; the user runs that once.

## Troubleshooting

- `MISSING TOOL: <x>` in a suite: that suite's tool (bun, python, pytest, go, cargo) is not installed. Install it or define the suite in `.modo-equipo-tests.json`.
- `No module named pytest`: `python -m pip install pytest`.
- Viewer shows black: the second screen may simply be empty; open a window there.
- Window appears on the wrong place after the display is re-added: run the launcher again.
